# 制約と次の着手点

## 引き継ぎ前に分かっていること

この会話の最新ユーザー依頼は「別スレへ必要データをまとめる」こと。新しい機能修正や特定の不具合修正を、今回のZIP作成に紛れて行ってはいない。
以下の優先順位は継続開発用の提案であり、新たにユーザーが依頼した機能の一覧ではない。

| 優先度 | 次の確認・作業 | 完了判断 |
| --- | --- | --- |
| 最初 | 元の署名鍵の所在と更新・移行方針を確認 | 既存データを守って今後のAPKを更新する手順が明確になる |
| 高 | 実機で起動、撮影／写真選択、画面幅とキーボード、下書き再開、保存まで確認 | 普段のAndroid環境で記録が1点登録でき、再起動後も見られる |
| 高 | ML Kitのモデル初回取得と背景除去を確認 | 表／裏を独立して切り抜き、失敗時も手動補正で保存できる |
| 高 | 実際のGemini API／モデルと応答形式を確認 | 名前・種類・上下位置・色を取得し、手入力を壊さず反映する |
| 高 | Google Cloud設定と2台で実Drive同期 | ログイン、フォルダ作成／参加、同時編集、通信断からの再試行、顔・裏・写真も収束する |
| 中 | メーカー別のウィジェットとDaydream確認 | 充電条件・ホームアプリ上で表示と切り替えが動く |
| 中 | 写真数が増えた際のサイズと表示性能を測る | UI、ZIP上限、HTMLサイズ、同期履歴の増加に現実的な運用を決められる |
| 中 | バックアップとアンインストールを含むデータ移行の実用確認 | 署名変更等が必要な場合も、事前バックアップから復元できる |

## 現行の制約・未実装

- GoogleログインとDriveの実サービスは未検証。同期コードがあることと利用者のGoogle Cloud登録が済んでいることは別。
- OAuthスコープはDrive全体。より狭い権限へ変えるなら、既存共有フォルダのURL指定と複数端末運用を維持できるか検討が必要。
- アプリを閉じている間の常時バックグラウンド同期はない。
- HTMLは閲覧用。PCからHTMLを編集してDriveへ同期する機能はない。
- 同じ服を別端末で別々に新規撮影した場合、画像による自動重複統合はない。
- セット選択による上下位置の自動固定・AIコーデ推薦はない。独立操作と関連リンクを実装している。
- ウィジェットは最大3枚の切り替え。ホーム画面の2段クローゼットをそのまま動かすものではない。
- 家族選択は顔写真のタップ。写真に写った顔から所有者を自動推定するものではない。
- バックアップ復元は同じIDの既存記録をスキップする。既存の記録を更新・統合したい場合と使い分ける。
- 写真を外しても履歴・古いファイルは即時に完全消去されない。履歴の整理・削除ポリシーは今後の検討事項。
- 元画像は長辺1280pxへ整えたもの。完全な高解像度の元カメラファイルは保持しない。
- 写真ファイルとSQLiteを跨ぐ電源断時の完全な原子性は保証しない。
- 現行のNative APIはMainActivityに集中している。大きく変える場合は既存移行・入力保持・表裏分離・同期テストを保ちつつ分割する。

## 変更時に回帰させないこと

表だけの簡単登録、手入力による救済、写真の画素を保持する切り抜き、2段の独立操作、顔の複数選択、相互リンク、写真の説明、旧データの移行、HTMLのオフライン閲覧、秘密情報の除外。UIだけでなく同期・ZIP・HTMLへ新フィールドを反映する。
